# UX 改进清单(定稿)

> 来源:wayfinder 地图「UX 系统性审视」(#24)终票「UX 改进清单定稿」(#30)。
> 输入:四份审计报告(`research/2026-ux-audit-{menubar-icon,popover-shell,focus-cards,notifications}` 分支 `docs/research/` 同名文件)、标尺与使用直觉(#29 决议)、#11 图标口径决议(本定稿对颜色半句作出修订,见文末「定稿决议」)。
> 范围:菜单栏图标、popover 主界面、通知三面;纯自用基准。红线:不触数据层/引擎策略(凭据、快照、解析、状态机、轮询)。
> 条目数:29 原始候选 → #29 合批 27 → 定稿 F/FC-1 再合批 = **26 条目**(P0×4、P1×5、P2×11、P3×6)。

## 标尺(摘要,#29)

- 价值 = 频率 × 痛感,定 P0–P3;痛感序:假安心 > 决策失效 > 白点一下/心算 > 不美观。
- 档内成本升序 tiebreak;审美仅并列微调;风险为约束不设轴。成本不作门槛。

## 验收工具约定(通用)

1. **popover / 图标条目**:DEBUG `--render-previews` 指定态 + OCR 必见文案;对比度类用审计同款像素取样法(含 8px padding 的渲染基线)。
2. **Core 文案条目**:`swift test` 断言更新即验收(UsageMonitorCoreTests)。
3. **纯审美条目**:人工 PNG 对照,不写 OCR 断言。
4. 需要时间流逝/陈旧态的验收,用 DEBUG 注入(虚拟时钟或时间偏移),不等待真实时钟。

## P0 · 立即

### P0-1 · IC-1 浅色菜单栏三色对比度

- **问题**:三色用系统 `.green/.yellow/.red`,浅色菜单栏下黄 1.31:1、绿 1.81:1、红 3.18:1(WCAG 小字线 4.5:1)——浅色为主的日常里,「偏低」态余光基本认不出。
- **改法**:`Presentation.color` 改外观感知调色板:浅色用加深变体、深色保持系统色;三态亮度阶梯化(黄最亮、红居中、绿最深),红绿色弱下仍可分档。浅色锚点(审计实测):黄 (190,140,0)≈2.61、绿 (34,128,28)≈4.34、红 (206,52,38)≈4.37。
- **验收**:render-previews 菜单栏浅色三态像素取样:黄 ≥2.5、绿 ≥4.2、红 ≥4.2;深色三态不回归(≥现状 6.56/8.70/3.51);OCR 数字识别率不降。
- **幅度**:呈现级(仅 `Presentation.color` + `colorScheme` 传入)。**成本**:小。

### P0-2 · 骨架A 总览条百分比扶正

- **问题**:全局结论「剩多少」埋在副行灰色句中段,每次打开 popover 都要读整句提取。
- **改法**:总览条右侧放状态色大号百分比(与图标数字同源同口径,`monospacedDigit`);副行保留「剩余 x/y 单位 · 重置 …」。
- **验收**:render-previews popover 正常/偏低/临界/错误四态(浅深)OCR 均见独立大号 %;数值与图标一致(同源 `GlobalOverview`)。
- **幅度**:呈现级。**成本**:小。

### P0-3 + P0-4 · IC-3 图标陈旧表达 + 骨架E 总览条最后成功标注(同批实施,各自验收)

- **问题**:轮询失败不清快照,连续失败/断网数天后图标照常显示旧数字,总览条同样不承认数字是旧的(焦点卡有诚实标记、结论位没有)——假安心。
- **改法**:图标用 **tightest 所属 provider 自己的 `lastSuccessAt`**(`EngineState.swift:21`,非全局 `lastUpdatedAt`),超阈值(2× 轮询间隔 = 60 分钟,展示参数)时数字降透明度或后缀「·」;总览条在最紧家 `loadFailed` 时副行追加「(最后成功 HH:mm)」——复用焦点卡既有口径。
- **验收**:DEBUG 注入陈旧态:超阈值图标带 stale 标记、未超不带;popover 错误态 OCR 总览副行含「最后成功」、正常态不含;成功刷新后标记消失。
- **幅度**:小新增。**成本**:小。

## P1 · 应做

### P1-1 · 通知批 C1+C2+C3+C5 文案信息量(Core,合并实施合并验收)

- **问题**:C1 临界通知不标窗口(GLM 5 小时窗可等滚动重置、7 天窗是整周见底,应对完全不同);C2 数字无千位分组,与 popover 同数不同形;C3「余额不可用,已达临界」措辞把账户级状态误导为用量耗尽;C5 identifier 固定「类型+provider」,GLM 双窗先后临界互相顶掉。
- **改法**(`EngineState.swift` 文案构造,测试断言跟随):
  - C1:文案插窗口 label——「GLM Coding Plan 7 天窗 剩余 3,000 积分(5%),已达临界」;label 空/不适用时回退现文案。
  - C2:remaining 经 `Money.formatCount` 千位分组。
  - C3:`accountUnavailable` 分支改「DeepSeek 账户余额不可用,请到平台查看」,不带「已达临界」。
  - C5:identifier 细化到窗口级(依赖 C1 已把 label 透出)。
- **验收**:`swift test` 文案断言 + identifier 断言更新(现有断言点 `UsageEngineTests.swift:352` 一带)。
- **幅度**:呈现级(文案)。**成本**:小。

### P1-2 · FC-5 DeepSeek 可用性严重性 + 删常态「可用」行

- **问题**:`is_available=false` 是普通 InfoRow 且暴露 API 字段名,卡内无强调;常态「可用状态 可用」行是纯噪音。
- **改法**:false 时余额块上方加红色内联条(复用 `failureStrip` 视觉):「官方标记账户不可用,以下为最后快照余额」,去 API 术语;true 时不渲染该行。
- **验收**:render-previews DeepSeek 卡不可用态 OCR 见红色内联文案、全文无「is_available」;正常态无「可用状态」行。
- **幅度**:呈现级。**成本**:小。

### P1-3 · FC-4 GLM 两个「7 天」口径命名碰撞

- **问题**:「7 天窗」(订阅锚窗剩余,积分)与「近 7 天用量」(自然滚动消耗,tokens)并排,口径与单位都不同,极易误读为同一件事。
- **改法**:消耗行文案向「近 7 天消耗 · tokens」方向,或加分组小标题区分「窗口剩余 / 累计消耗」;`.failed` 态配 tooltip 说明该行依赖独立时序接口。文案遵循 CONTEXT.md `rollingUsage` 词条(统一「近 7 天」,不回退「本周」)。
- **验收**:render-previews GLM 卡 OCR 两行口径可区分;词汇不回退。
- **幅度**:呈现级。**成本**:小。

### P1-4 · 骨架F + FC-1 时间相对化合批(重置倒计时 + 上次更新相对化 + 失败态过期标注)

- **问题**:重置/更新的绝对时间都要心算「还有多久/多旧」;失败态旧快照的重置时间可能**已经过去**却无标注(误导)。
- **改法**:共享相对时间 formatter,分档:`resetAt − now` <1h「约 N 分钟后重置」、<24h「约 N 小时后重置」、跨天保留日期(绝对时间进 tooltip);脚注「上次更新」改「N 分钟前更新」(>1h 退回绝对);卡内窗口行同行补倒计时;失败态已过期的重置时间降灰并标「已过期(最后成功快照)」;`TimelineView(.periodic)` 仅 popover 可见时刷新文本。
- **验收**:DEBUG 时间注入下 OCR:总览/窗口行含「约 N (分钟|小时)后重置」;脚注含「N 分钟前更新」;errors 态过期重置行含「已过期」;formatter 分档边界(59min/1h/23h/24h/跨天)有单测。
- **幅度**:呈现级(含小新增定时器)。**成本**:中。

### P1-5 · 骨架C 凭据状态行全绿收拢

- **问题**:凭据配好后常年全绿,三行「已配置 · 管理」在固定高 430 内挤压总览与焦点卡;该行真正有信息量的时刻横幅也在场。
- **改法**:全部已配置且无读取失败时收成一行「三家凭据正常 · 管理」;有问题时只展开问题家(横幅管汇总、行管逐家入口,分工不变)。
- **验收**:正常态 OCR 一行;错误/失效态逐家行保留、横幅分工不变。
- **幅度**:呈现级。**成本**:小-中。

## P2 · 顺手(档内成本序)

### P2-1 · G 刷新过程可见反馈

- **问题**:打开 popover 自动刷新无指示,数据到位原位跳变,「点了没反应」体感真实。
- **改法**:刷新中在总览条尾部或脚注给轻量 spinner/「刷新中…」;完成瞬间「上次更新」文本短暂高亮。呈现层消费 `isRefreshing`。
- **验收**:DEBUG 注入 isRefreshing 态 OCR 见「刷新中…」;完成高亮人工确认。
- **幅度**:小新增。**成本**:小。

### P2-2 · FC-2 窗口行内剩余百分比

- **改法**:行尾 muted 小字「(95%)」,口径与 `displayPercent` 一致,与图标/总览互证。
- **验收**:render-previews 各窗口行 OCR 含 %;与图标同口径。
- **成本**:小。

### P2-3 · 口径复核批 IC-4+IC-5:图标颜色跟随数字口径(定稿选型乙)

- **问题**:颜色(全局最差 status,含 DeepSeek 余额档位)与数字(最紧 plan-window 剩余%)常来自不同 provider——「红色 65%」读不出红的是谁;DeepSeek-only 时图标永久灰「—」零信号。
- **改法**:颜色改随数字口径——有窗口快照时,颜色 = **最紧窗所属 provider 的 status**(即最紧窗自身档位);无窗口(DeepSeek-only / 首刷未回)时 = 余额档位给色的「彩色 —」。DeepSeek 余额临界在图标上退场,由临界通知 + 总览条兜底。本条修订 #11 决议的颜色半句(见文末)。
- **验收**:构造 DeepSeek 临界 + GLM 窗 65% 态:图标绿 65%(不再红);DeepSeek-only 临界态:彩色「—」;纯窗口态颜色不回归;「红 65%」形态从渲染矩阵消失;`GlobalOverview` 相关测试跟随。
- **幅度**:呈现级(取色消费处)。**成本**:小(#29 估小-中,选型乙后回落)。

### P2-4 · 通知C4 popover/设置可见时不打扰

- **问题**:popover 可见时会触发刷新,若恰好跨入临界,正看卡片又收横幅+声音——同屏双通道说同一件事。
- **改法**:`willPresent` 注入可见性闭包(与 `onOpen` 同路),popover 或设置窗口可见时返回 `[]`(仍进通知中心,不横幅不响)。
- **验收**:DEBUG 手动两场景(打开 popover 触发跨临界 → 无横幅、通知中心有记录;关闭后恢复);现有 presenter 测试跟随。
- **幅度**:呈现级(适配层)。**成本**:小-中。

### P2-5 · B 轻量 tab 百分比

- **改法**:tab 文本追加各家 plan-window 最低剩余%(无快照家显「—」),数字用状态色。
- **验收**:render-previews 三 tab OCR 各含 % 或「—」。
- **成本**:小。

### P2-6 · FC-3 Kimi 卡分层:额度窗口 vs 次级事实

- **问题**:频限窗与套餐窗同权重、label 冗长;滚动窗「重置」与套餐窗「重置」同词不同义;并发上限常量与动态额度混排。
- **改法**:卡内分两区——「额度窗口」主区;次级区(更小字号/次要色):频限单行「频限 90/100 请求 · 滚动 300 分钟」、并发并入;频限避免「重置」一词(如「容量恢复 08:56」)。
- **验收**:render-previews Kimi 卡 OCR 见两区、频限单行化;人工 PNG 看层级。
- **幅度**:呈现级(分层)。**成本**:中。

### P2-7 · IC-2 a11y 一行 label

- **改法**:图标 label 加 `.accessibilityLabel`:「全局最紧剩余 65%,GLM 7 天窗;最差状态:DeepSeek 临界」形态(label 可同时报全局最差,补足乙选型后图标本体的口径收窄)。
- **验收**:离屏渲染管线顺带打印 accessibilityLabel 文案供核对(或 Accessibility Inspector 手检)。
- **成本**:小。

### P2-8 · I 双「刷新」作用域区分

- **改法**:卡脚按钮改「刷新(仅本家)」,或非失败态移除卡级刷新、失败态保留「重试」;头部保持全量语义。
- **验收**:render-previews 正常/错误态 OCR 作用域可辨、无并存「重试+刷新」。
- **成本**:小。

### P2-9 · FC-6 Kimi plan 胶囊去内部域码

- **改法**:胶囊只显 level;domain 进 `.help`(tooltip);已知域值在展示层映射(不动解析层)。
- **验收**:render-previews Kimi 卡 OCR 无「DOMAIN_NEXUS」。
- **成本**:小。

### P2-10 · D 删横幅图例副文案

- **改法**:删「凭据状态:已配置 / 未配置 / 已失效」;fresh 态(全新安装)可保留。
- **验收**:render-previews 正常态横幅单行;fresh 态两行。
- **成本**:小。

### P2-11 · FC-7 进度条颜色语义统一

- **问题**:正常态进度条 `.accentColor`(蓝)与状态点绿分叉,同卡两种「好」色。
- **改法**:二选一全局统一,推荐克制版:全套中性灰、仅告警(黄/红)变色;备选正常态 tint 改绿。
- **验收**:人工 PNG 对照,同一规则覆盖全部 plan 窗进度条。
- **成本**:小(纯审美压底)。

## 定稿决议(#30,grilling 与本人对话拍板)

1. **图标口径(选型乙,修订 #11 颜色半句)**:图标颜色随数字口径——有窗口快照时 = 最紧窗所属 provider 的 status;无窗口时 = 余额档位给色的「彩色 —」。#11 原「颜色 = 全局最差 status(DeepSeek 档位可拉低)」废止;数字 = 全局最低 plan-window 剩余%、阈值、灰「—」规则不变。
2. **通知文案留在 Core**:C1–C3 属文案非策略,测试断言跟随;「文案住壳层」的结构议题不采纳。
3. **无条目原型先行**:呈现级用 render-previews 自检;P3 备查项提拔时再原型。
4. **顺序**:#29 初排照单;骨架F+FC-1 合批(共享相对时间 formatter)。
5. **验收形态**:三档(OCR 可断言 / swift test / 人工 PNG),见文首「验收工具约定」。
6. **越线确认**:无条目需另立地图。唯一越线项(临界发现时机受 30 分钟轮询约束 = 改引擎策略)审计时已判死存档。
7. **ADR 判否**:全部条目为可逆呈现层变更(改回即回),不满足「难以逆转」门槛;#11 口径修订记录于本文件与 #30 决议评论,不立 ADR。
